Why Is My Scanned PDF So Large?

This is genuinely the most common reason people search for a PDF compressor. A typed document stores its content as text data — a few kilobytes even across several pages. A scanned document is completely different: the scanner captures the entire page as a photograph, including every part of the blank margin, and embeds that image inside the PDF. There's no text data to fall back on, only pixels.

A single A4 page scanned at 300 DPI in full colour produces roughly 2,480 × 3,508 pixels. Even with the PDF format's own internal image compression, that typically comes out to 2–4 MB per page. A five-page certificate bundle can easily reach 15–20 MB before any compression at all — nowhere close to a 100KB or 200KB portal limit, and a common source of confusion for anyone comparing a phone's "file size" reading against what the application form actually asks for.

Two things fix this at the source, before compression even starts. Scan resolution: most government and banking portals only need to verify that text and seals are legible on screen, not print quality, so scanning at 150–200 DPI instead of 300 DPI cuts the raw file size dramatically with no visible loss for on-screen review. Colour mode: a black-and-white or grayscale scan is a fraction of the size of a full-colour one for a document that's mostly text on white paper. Combine a lower-DPI, grayscale scan with this compressor's target-size mode, and even a heavily scanned multi-page certificate reaches 100KB comfortably.

100KB vs. 200KB vs. 500KB — Which Target Should You Use?

Not every portal enforces the same cap, and guessing wastes time. Here's how to decide without trial and error:

100 KB

The tightest common limit. Used by several SSC-affiliated and state PSC portals, and by NSP's scholarship portal after its 2025–26 revision. If your notification doesn't state a number, 100KB is the safest target to prepare for.

200 KB

A common middle ground for certificates and marksheets across SSC, Railway RRB, and several college admission portals. Gives slightly more room for detail in scanned seals and stamps than 100KB.

500 KB – 1 MB

More generous limits typical of UPSC, EPFO, and passport/OCI applications. Preserves more visual detail, useful for multi-page or heavily-illustrated documents.

The compressor on this site accepts any custom target, not just these three — type your exact portal limit and the tool works toward that number specifically, rather than offering only fixed presets.

How to Scan Documents That Compress Well

Compression can only do so much with a bad starting scan. A few habits at scan time make the difference between a 100KB file that's still crisp and one that's compressed into illegibility:

  • Scan at 150–200 DPI, not 300 DPI — for on-screen verification, higher resolution just means a larger file with no visible benefit to the reviewer.
  • Use grayscale or black & white for text documents — a colour scan of a mostly-black-and-white certificate wastes file size on colour data nobody needs.
  • Crop tightly to the page edges — extra background or desk visible around the document adds size without adding information.
  • Use even, direct lighting — a well-lit scan compresses more cleanly than a shadowed one, since compression algorithms work harder (and lose more detail) on uneven contrast.
  • Flatten multi-page scans into one PDF first — compressing one combined file gets more consistent results than compressing separate pages individually.

Fixing "File Size Exceeds Limit" Upload Errors

This exact error message is what sends most people looking for a compressor in the first place, usually at the worst possible moment — minutes before an application deadline. Here's how to fix it without panicking:

Check the actual file size first

On Android, long-press the file in your file manager for a details panel. On iPhone, tap the "i" info button in the Files app. On a computer, right-click and choose Properties (Windows) or Get Info (Mac). Knowing the exact size tells you how aggressively to compress.

Compress to a target, not a guess

Rather than repeatedly re-compressing and re-checking, set your exact target (100KB, 200KB, whatever your notification states) once and let the tool iterate for you.

Confirm the format matches

A correctly-sized file in the wrong format (PNG where JPEG is required, or a DOCX where PDF is required) fails the same way a too-large file does. Double-check the portal's format requirement alongside the size.

Reducing PDF Size Without Losing Quality: What Actually Changes

"Without losing quality" is doing real work in that phrase, and it's worth being precise about what it means. Compression doesn't magically remove bytes for free — it trades one specific kind of visual detail (fine gradients, subtle colour variation, extremely high resolution) for a much smaller file. What it does not touch is legibility of text, overall document structure, or the presence of official seals and stamps, provided the compression level is chosen sensibly.

The practical rule of thumb: text-heavy documents (typed letters, most certificates) tolerate aggressive compression extremely well, since text itself barely contributes to file size in the first place. Documents where fine visual detail actually matters — a photograph, a detailed technical diagram, a document where subtle color differences carry meaning — need a gentler compression setting to avoid visible quality loss. For the certificates, marksheets, and ID documents most people are compressing for portal uploads, the aggressive end of compression is almost always the right choice, since verification depends on reading text and recognizing a seal, not appreciating image nuance.

What Actually Happens Inside a PDF During Compression

A PDF is a container, not a single blob of data. Inside it lives text (stored as compact vector/font data), embedded images, metadata (author, creation software, timestamps), and sometimes form fields or annotations. When text dominates a document, the file is already small — a ten-page typed contract might be under 200KB before any compression at all, since text data is inherently lightweight.

Compression targets the two components that actually take up space: embedded images and metadata. Images get re-encoded at a lower quality setting — similar to how a JPEG's quality slider works, trading a small amount of visual fidelity for a large reduction in file size. Metadata like embedded thumbnails, unused fonts, and editing history gets stripped entirely, since none of it is visible or necessary once the document is finalized. Text itself is essentially untouched in this process, which is exactly why a compressed PDF keeps its words sharp and legible even when the file shrinks by 90% or more.

For a purely scanned document — where the entire page IS an image, with no separate text layer — nearly all of the file size reduction happens through image re-encoding, since there's no text/metadata split to work with. This is also why scanned PDFs compress dramatically (routinely 85–95%) while a text-heavy typed document might only shrink by 20–30%, simply because there was much less "image weight" to remove in the first place.

Applying to Multiple Portals? Combine Certificates First

Many applications ask for "all supporting documents in a single PDF" rather than separate files per certificate. Compressing several already-merged pages together, in one pass, gives more consistent, predictable results than compressing five separate small PDFs and hoping each lands under the limit individually.

The recommended order: scan each document individually at 150–200 DPI in grayscale, combine them into one PDF using a PDF merger tool, then compress the combined file to your target size once. This avoids the awkward situation of five individually-compressed files that, added together, still exceed a combined upload cap — a real constraint on several scholarship and admission portals that treat "supporting documents" as a single upload slot.

PDF, Image, KB, DPI — A Quick Glossary

Government portal instructions throw around several related-but-different terms in the same sentence. A quick, precise reference:

PDF vs. Image (JPG/PNG)

A PDF is a document container that can hold text, images, and layout together across multiple pages. A JPG or PNG is a single image file. A "scanned PDF" is really an image wrapped inside a PDF container — which is why it behaves more like a photo, size-wise, than a typed document.

KB vs. MB

1 MB (megabyte) equals 1,024 KB (kilobytes). A portal asking for "under 100KB" wants a file roughly a tenth the size of a typical 1MB phone photo — this is why raw phone camera photos almost always need compression before they qualify.

DPI (Dots Per Inch)

DPI measures scan resolution — how many dots of detail are captured per inch of the original page. Higher DPI means a sharper but larger file. 150–200 DPI is enough for on-screen document verification; 300 DPI is meant for print quality most portals don't actually need.

Compression vs. Resizing

Compression reduces file size by re-encoding image quality without changing the page's visible dimensions. Resizing changes the pixel dimensions themselves. Most portal requirements are stated as a file size (KB), which compression addresses directly — resizing is a separate, less commonly required step.

Candidates who prepare their document set in advance — scanned, correctly sized, and saved somewhere easy to find — move through the actual application form far faster than those scrambling to scan and compress documents for the first time on deadline day.

A practical habit: keep one folder with your most commonly-needed documents (educational certificates, category certificate, ID proof) already scanned at 150–200 DPI in grayscale, and one compressed copy of each at a conservative 100KB target. Since most portals accept 100KB or higher, a file already prepared at 100KB works for the vast majority of applications without needing to be redone from scratch — you only need to re-compress to a larger target on the rare occasion a specific portal is unusually generous with its limit.

This preparation takes perhaps twenty minutes once, and then saves that same twenty minutes (or more, under deadline pressure) every single time a new application opens throughout the year. For candidates applying to multiple exams across a recruitment season, that adds up to meaningful saved time and, more importantly, one less way for an application to fail for reasons that have nothing to do with actual eligibility or preparation.

Choosing Between Target Size and Compression Level

Most compressors offer two related but different controls: a specific target file size (like "100KB") and a compression level (often labelled Low, Medium, or High, or sometimes described as favouring quality versus size). Understanding the difference avoids a common source of confusion when a document doesn't come out quite the size expected.

A target size tells the tool the destination — it will iterate through compression settings automatically until the output lands at or under that number. This is the simpler, more predictable choice when a portal states an exact KB limit, which covers most government exam and scholarship use cases. A compression level, by contrast, applies a fixed setting regardless of the source file — useful when there's no hard size requirement, just a general goal of "make this smaller," but less precise when a specific number matters.

For portal uploads specifically, target-size mode is almost always the better choice: enter the number from your notification (100KB, 200KB, whatever it states), and let the tool handle the rest rather than guessing at a compression level and re-checking the result manually. This is also the safer default when preparing several documents in a row — each one gets tuned to hit the same target independently, regardless of how large or detailed the original scan was.

Privacy: Why Offline Processing Matters for Government Documents

Every document discussed on this page — Aadhaar cards, category certificates, marksheets, bank passbooks — carries information most people would rather not hand to an unfamiliar server, especially when a tool only needs to resize the file, not read what's inside it. This isn't a hypothetical concern: a compressed file still contains the full original content, just re-encoded at a smaller size, meaning a server that receives it for "compression" has full access to everything on the page during that process.

A tool that runs entirely in your browser using WebAssembly never transmits the file anywhere in the first place. Nothing is uploaded, so there's nothing sitting on a remote server to be retained, logged, or potentially exposed later. It also means the tool keeps working through an unreliable connection — once the page has loaded, you can switch to airplane mode and compression still completes, since your own device is doing the work rather than a server on the other end.

This is a genuinely different approach from most free PDF compressors, which upload the file to a server, process it there, and send the result back — a round trip that's often unnecessary for a task as simple as resizing. For a one-off task involving no personal data, the difference may not matter much. For a document that includes an Aadhaar number, date of birth, category, or family income details, it's worth knowing which kind of tool is actually being used before uploading anything to it. If you ever need to double-check, open your browser's developer tools and watch the Network tab while compressing — you'll see no outgoing request carrying your file, which is the simplest way to confirm the claim rather than just taking it on faith.
